# claude-billing

Shell utility (sourced, not executed — must work in bash AND zsh) that switches Claude Code between billing modes by editing `~/.claude/settings.json` and shuffling OAuth tokens in the platform credential store.

## Files

- `claude_billing.sh` — everything: helpers, credential abstraction, account registry, `claude_billing()` dispatcher, `claude-billing` alias
- `install.sh` — curl-pipe installer; adds `# >>> claude-billing >>>` block to RC file and installs the menu bar helper on macOS
- `platform/macos/install-menubar.sh` — optional macOS menu bar app builder, login-item installer, and standalone uninstaller
- `menubar/` — native AppKit app plus Swift package tests
- Installed to `~/.claude-billing/`; version in `_CB_VERSION` (bump on release, separate chore commit)

## Architecture

- Credential store per platform: macOS Keychain (`security`), Linux GNOME Keyring (`secret-tool`), Windows Git Bash `~/.claude-billing-credentials` (chmod 600). Abstracted via `_cb_cred_store/retrieve/delete`.
- Live OAuth token: keychain service `Claude Code-credentials`. Legacy single backup: `Claude Code-credentials-backup`. Named subscription accounts (v1.1.0+): `Claude Code-credentials-acct-<name>`.
- Account identity metadata: Claude Code stores the logged-in account's identity (`oauthAccount`: account/org UUIDs, subscription type) in `~/.claude.json` — if it doesn't match the live token, Claude Code forces re-login. Per-account stash: `Claude Code-oauthAccount-acct-<name>`; swapped into `~/.claude.json` on restore via jq (`_cb_acct_meta_backup/_restore`). Best-effort: failures warn but don't abort the switch. Legacy (account-less) flow never swaps it — same account, still matches.
- Account registry: `~/.claude-billing-accounts` (keys `CLAUDE_BILLING_ACCOUNTS` space-separated, `CLAUDE_BILLING_ACTIVE`). Active account's token is always the live one; inactive accounts hold stashed tokens. `_claude_billing_backup_oauth` stashes into the active account's slot (or legacy backup if none) and clears active.
- Once accounts are registered, `subscription`/`sub` requires a name; account-less usage keeps legacy single-backup behavior (backward compat).
- Bedrock config: `~/.claude-billing.conf` (region, model IDs incl. Fable, AWS profile mode).
- Desktop app (Claude.app, macOS): login = `Cookies` SQLite (sessionKey, values encrypted by per-machine "Claude Safe Storage" keychain key — swappable between accounts) + `oauth:tokenCache`/`oauth:tokenCacheV2`/`lastKnownAccountUuid` in the app's `config.json`. Stashed per account in `~/.claude-billing/desktop/<name>/`; owner tracked in `desktop/.active`, fully independent of `CLAUDE_BILLING_ACTIVE` (v1.2.0+): the desktop only ever holds a subscription login, so it's switched ONLY by the explicit `desktop <name>` command — CLI billing switches never touch it (`subscription` prints a hint when desktop owner differs). First `desktop` switch prompts for who owns the live login (seeds `.active`); unknown owner → safety copy in `desktop/.unclaimed`. App must be quit before swap (Chromium rewrites cookies on exit); `_cb_desktop_quit` prompts + osascript. If Claude.app was running before a successful swap, `_cb_desktop_launch` reopens it; leave an already closed app closed. A failed or cancelled explicit Desktop switch returns an error without changing the tracked owner.
- AWS SSO expiry (v1.3.0+): read-only reporting for Bedrock profiles. `_cb_sso_config_rows` parses `~/.aws/config` (awk) into `S`/`L`/`P` rows (sso-session block, legacy profile with its own `sso_start_url`, profile→session link); `_cb_sso_cache_json` collects `{key, url, expiresAt}` from `~/.aws/sso/cache/*.json`, where `key` is the filename (falls back to per-file jq so one malformed file can't hide the rest); `_cb_sso_rows_with_keys` appends the expected cache key per login — the AWS CLI names token files `sha1(<sso-session name>)` for session-style logins and `sha1(<start url>)` for legacy profiles, so matching on the key (not just the URL) is what keeps expiry in agreement with the CLI: renaming a session orphans its token and must read as signed out. `_cb_sha1` tries shasum/sha1sum/openssl and prints nothing if none exist, in which case matching falls back to the start URL. `_cb_sso_status_json <active-profile>` joins them, groups by start URL (an `[sso-session]` name wins over a legacy profile name), and emits `{name, kind, startUrl, profiles, expiresAt, secondsRemaining, status, active}`. Status thresholds: `expired` (<=0), `expiring` (<=1800s), `valid`, `signed-out` (no cached token — the AWS CLI deletes it on logout). Expiry maths is jq (`fromdateiso8601` after stripping fractional seconds); `_cb_now` honours `CLAUDE_BILLING_TEST_NOW` so tests are deterministic. Exposed as `sso [--json]`, in `status`/`status --json` (`awsSso`), and refreshed by `sso-login <session>` which picks `aws sso login --sso-session` for session-style logins and `--profile` for legacy ones. Never write to the SSO cache; the AWS CLI owns it.
- Subscription plan usage (v1.4.0+, reworked in v1.5.0): `_cb_usage_fetch_one` GETs `https://api.anthropic.com/api/oauth/usage` (header `anthropic-beta: oauth-2025-04-20`) with the account's OAuth access token — the same request Claude Code's `/usage` view makes. UNOFFICIAL, unversioned endpoint: consume only the normalized `limits[]` (`kind`, `group`, `percent`, `severity`, `resets_at`, `is_active`) and `spend`; the sibling code-named keys (`amber_ladder`, `nimbus_quill`, …) are internal, do not read them. Any non-200/parse failure returns `status: unavailable` — never a percentage, and never fatal to a switch. Credentials are READ-ONLY here: use a stashed token as-is, never refresh/rewrite/delete one to read usage, so an expired access token reports `token-expired` (switching to that account makes Claude Code refresh it). The token goes to curl via `--config -` on stdin, never argv (ps exposure). Requests identify as `claude-code/<version>` (`_cb_usage_user_agent`, reading `claude --version`, falling back to `_CB_USAGE_UA_FALLBACK`, memoised per shell): the endpoint is Claude Code's own and rate-limits clients it doesn't recognise — claude-billing's own User-Agent drew 429s at a five-minute cadence. Every emitted entry carries `tokenExpired`, computed locally by `_cb_usage_token_expired` from the stored credential's `expiresAt` — no request, so it is known even for an account that was deliberately not polled (`--active`) or is inside a backoff window. In the menu that greys the account's meters and blanks their percentages (`meterItem(isStale:)`) while KEEPING the credit balance — money in the account doesn't go stale the way a rolling window does — and adds a secondary-grey `alertItem` (glyph, not orange type) under the figures. Do not delete stale figures outright: roughly where you stood beats a blank, provided it can't be mistaken for current. Rate limits are BACKED OFF, not retried: `_cb_retry_seconds` honours `Retry-After` (seconds form; the HTTP-date form is not handled) or defaults to 900s for a 429, clamped to 60..3600, and `_cb_usage_json` stores the deadline per account under the cache's `retry:until` key (a colon can't appear in an account name, so it can't collide). A stored wait outranks `--refresh` — clicking Refresh again is what earns the throttling in the first place — and is cleared by the next successful read. `_cb_header_value` reads the header out of curl's `dump-header` file, which holds response headers only and never a token. `_cb_usage_json [--refresh] [only-account]` restricts network calls to `only-account` (`-` for the legacy account-less entry) and serves the rest from cache, or `not-polled` when nothing is cached — the endpoint rate-limits (HTTP 429) and an account you are not on is not spending its limits, so polling it only burns the budget of the account you care about. It serves `~/.claude-billing/usage-cache.json` (chmod 600, TTL `CLAUDE_BILLING_USAGE_TTL`, default 300s) and, when a refresh fails, keeps the last good entry with `ageSeconds`/`staleReason`; `ageSeconds`/`staleReason` describe the read and are stripped before caching. Prepaid credit balance is a SECOND unofficial request: `_cb_credits_fetch_one` GETs `/api/oauth/organizations/<org>/prepaid/credits` (org UUID via `_cb_usage_org_uuid`: `~/.claude.json` for the active account, the stashed `oauthAccount` for others). It is strictly additive — no org, non-200, or unparseable body yields no `credits` key and must never degrade the plan figures. Balance is `balance.credits.amount_minor` over `10^exponent`; `expiringAmount` totals the tranches (including `promo_tranches`) sharing `next_expires_at`. Exposed as `usage [--json] [--refresh] [--active]`, where `--active` resolves the registry's active account and passes it as `only-account`; the menu bar always passes it. Deliberately NOT part of `status --json`, which must stay offline and fast (the menu bar polls it on the shared 300s beat and again on every menu open).
- Prompt indicator: every switch writes the mode (`sub`, `sub:<name>`, `api`, `bedrock:<profile>`) to `~/.claude-billing-mode`; `claude_billing_prompt` prints it for shell prompts, and `status` resyncs the file from settings.json (source of truth). Bedrock resolves the profile from explicit settings first, then inherited `AWS_PROFILE`, then `default`. User's machine wires it via a `[custom.claude_billing]` module in `~/.config/starship.toml` and a billing segment in `~/.claude/statusline-command.sh` (both user-local, not in repo).
- Menu bar app (macOS 13+): `menubar install|uninstall` delegates to the helper installed by the normal macOS installer. The app calls the installed shell function through `/bin/zsh` and consumes `status --json`; never duplicate settings or credential transition logic in Swift. Account names are passed as separate process arguments. Its rounded template badge maps subscription/API/Bedrock to `S`/`A`/`B`; AWS SSO expiry is deliberately dropdown-only and must never alter the badge: it gets its own `AWS SSO sessions` row (with submenu) below the Bedrock row, each item opening `sso-login` in Terminal. Keep Bedrock a one-click `actionItem` — AppKit ignores the action of an item that owns a submenu, so SSO must never be nested under it. `ssoMenuTitle` carries the stale-session count so a lapsed login is visible without opening the submenu, and every session shows `profileSummary` (the AWS profiles it signs in) because the session name is a user-chosen label from `~/.aws/config` and conveys nothing about which accounts it reaches; detailed account/profile context belongs in the tooltip and grouped dropdown, explicitly labeled as Claude Code CLI state. JSON status also exposes the independent Claude Desktop owner, and the dropdown delegates Desktop choices to `desktop <name>` after an AppKit confirmation. Use native, unindented menu sections, one per provider (subscriptions, then Bedrock with its SSO row, then the API key — no combined "other billing" bucket), and keep the dropdown free of standing advisory rows (no restart reminder, no endpoint disclaimer — those belong to the README and CLI output). Only groups whose rows can't name themselves get a header, so there is no separate current-mode row (the checkmark carries it). The current mode must stay enabled (`isEnabled = !isSwitching`) because a greyed row reads as unavailable; `switchClicked` ignores clicks on a `.on` item so an already-active mode is never re-transitioned. Claude Desktop accounts live in a submenu on the Desktop row so a bare account name can never appear twice at top level. Read-only detail lines (SSO profiles, usage figures) use `detailItem` — small secondary attributed text — never space-indented disabled rows. `bedrockRowTitle` names the profile a switch would select only when deterministic (`bedrockProfileSource` of `settings`/`config`); inherited resolves to "inherited profile"; Desktop choices use an ellipsis because they require confirmation. The management submenu validates new account names, confirms removals, and delegates removal with `remove-account <name> --yes`; interactive add-account, Bedrock, API-key, and login flows open a temporary, safely quoted Terminal script and remain CLI-owned. An AppKit progress indicator replaces the badge while an in-app operation runs, and timer refreshes must not overwrite that transient state. It uses the same mode cache as prompts/statuslines. One `refreshInterval` (300s) drives both the billing-state and usage timers, and `menuWillOpen` refreshes state synchronously-then-async so a slow background beat is never what the user reads; `Refresh` forces both (`refreshState` + `refreshUsage(force: true)`). Plan usage still runs on its own timer (guarded by `isLoadingUsage`) so a network call never delays billing state, and its tick forces a fetch because the interval equals the CLI's default cache TTL, so a cached read would stall the meters an extra interval. `rebuildMenu` repopulates ONE persistent `NSMenu` (`menu.removeAllItems()`) — assigning a new `statusItem.menu` dismisses an open menu — and state refreshes only rebuild when the state or error message actually changed. The `Plan usage` row trails a secondary-text `usageFreshnessNote` after its bar, and each submenu account carries the same note beside its NAME (`sectionItem(title:detail:)`) because freshness qualifies every figure in that group — never trailing under it. `UsageAccount.staleNote` is then the REASON alone ("not refreshed — …"), shown only when there is one; `usageAgeSeconds` takes the greater of the CLI's cached age and time since this app's last successful fetch, so a forced fetch reads "just now" while a failed refresh keeps the honest stale age, and lives in a `Plan usage` row + submenu under the subscription accounts; live figures use `labelColor` and only stale ones dim (dimming must mean "no longer true" and nothing else) — which requires the usage submenu to set `autoenablesItems = false` and live `meterItem`s to be `isEnabled = true`, because AppKit greys a DISABLED item's text whatever colour its attributed title asks for; the rows have no action, so nothing is clickable, and a stale row stays disabled so AppKit dims it for us. The expired-token `alertItem` is secondary grey with a glyph, NOT orange type: orange reads as an emergency and an expired token is an errand; limits render through `meterItem`, whose image is a real filled bar drawn by `usageBarImage` (non-template, or AppKit recolours it) sitting in the icon column, followed by the percentage in monospaced digits and a secondary-text label. `usageBarFillWidth` holds the geometry rules and is unit-tested separately from drawing: >0% always leaves a 3pt sliver, <100% never fills the track, out-of-range clamps. The credits row reports spend against the monthly cap (`spend.used` of `spend.limit`) with a currency symbol. Do NOT relabel it a "balance": `/api/oauth/usage` exposes no prepaid credit balance, only spend and cap. `UsageLevel` fixes the thresholds — green <60, orange <85, red >=85 — deliberately NOT the endpoint's own `severity`, so a percentage always maps to the same colour. The top-level row carries its level in the icon column instead of a progress bar: `usageLevelIcon` draws a three-bar chart with `UsageLevel.litBars` lit (1 green / 2 orange / 3 red, unlit bars in `tertiaryLabelColor`), non-template so AppKit can't recolour it. Count and colour encode the same thing on purpose, so the row survives being read without colour vision. Do NOT put a wide progress bar back in that row's image: a menu item's image always precedes its title, so a 46pt bar there indents the label past every other row (`usageBarImage` stays for the submenu's `meterItem`s, where a percentage per limit is the point). It shows the bar, the percentage, and the reset time (the wait is information the bar can't carry). The usage rows carry NO tooltips: hover text hides information behind a gesture nobody makes in a menu, so anything worth knowing is on screen — which is why the failure row prints the whole problem rather than its first clause. Accessibility labels are not hover text and stay. `statusSuffix` owns that text: a `session` limit has no `resets_at` until the window opens, so an unstarted one must read "not started" and never imply a deadline. The row always headlines the 5-hour `session` limit (only falling back to the tightest other limit when the endpoint omits it), the single `Refresh` item forces a usage fetch (no separate refresh action in the submenu). It must stay an ordinary `NSMenuItem`: giving it a custom `view` to keep the menu open BREAKS it outright — AppKit stops firing the item's action once a view is set, and the menu's own tracking consumes the click before the view sees it, so nothing runs. Instead `refreshClicked` records `refreshClickedAt` and `reopenMenuIfRequested` re-presents the menu via `statusItem.button?.performClick(nil)` from the usage completion (the slow half), so it comes back holding the new numbers. That reopen is guarded two ways: a time rather than a flag (`reopenWindow`, 10s) so a fetch that never runs can't make a later timer tick pop the menu open unprompted, and `refreshUsage` returning whether it actually started so a click during an in-flight fetch reopens immediately instead of waiting forever, the submenu carries no source/disclaimer note (that caveat belongs to the README and CLI output), and failures must render as a reason, never 0%. A refresh that fails while readable figures are still on screen is a THIRD state, distinct from both fresh and unreadable: `refreshFailure` (`staleReason` on an otherwise-ok account) puts a bare orange `exclamationmark.triangle.fill` in the row via `symbolAttachment` (an inline `NSTextAttachment`, because the row's one image slot already holds the level icon). The glyph ONLY: the reason is a sentence of API detail and belongs to the tooltip and the submenu's `ageNote`, not the row. Without it, clicking Refresh and seeing an unchanged number reads as Refresh being broken. HTTP statuses get named causes in `_cb_usage_fetch_one` (429 rate limited, 401/403 login rejected, 5xx upstream trouble) rather than a bare code, because a bare code reads as a claude-billing bug. Login items generally do not inherit terminal-scoped `AWS_PROFILE`, so an inherited Bedrock profile normally resolves to `default`; explicit profile mode is deterministic.
- Installer updates are atomic: download and syntax validation happen in a same-directory temporary file, and the existing installed script is replaced only after validation succeeds.
- API, Bedrock, and legacy subscription switches restore the prior settings backup when OAuth backup, restore, or login fails. Do not write the mode cache or print success until the full transition succeeds.

## Gotchas

- zsh parses `${var//%s/replacement}` as an END-ANCHORED replacement (`/%` anchor), so a `%s` placeholder silently eats the last character instead. Build URLs and paths by concatenation. This bit us once.
- zsh does NOT word-split unquoted variables — iterate lists via `$(command substitution)` (zsh splits those). This bit us once.
- Guard positional params with `${2:-}` (users may have `set -u`).
- Store-before-delete ordering for all token moves — never delete a token until its copy is confirmed written.
- Credential deletion failures must remain visible and retryable: keep account registration when removal fails, and return a warning status from uninstall when secrets may remain.
- Match installer blocks and legacy source lines exactly when editing shell RC files; unrelated mentions of `claude-billing` belong to the user.
- `_cb_read` reads from `/dev/tty` when readable (curl-pipe installs).
- macOS `security add-generic-password -w` exposes value briefly in ps; no stdin option exists.

## Testing

- Static checks: `bash -n claude_billing.sh install.sh platform/macos/install-menubar.sh test/run.sh`, `zsh -n claude_billing.sh install.sh test/run.sh`, and `shellcheck claude_billing.sh install.sh platform/macos/install-menubar.sh test/run.sh`.
- Behavioral suite: run both `bash test/run.sh` and `zsh test/run.sh`. `seed_aws_sso_fixture <home>` builds a fake `~/.aws` (shared start URL, trailing slash, fractional seconds, stale duplicate, malformed cache file); it takes the home directory as an argument because each test runs in its own subshell and shellcheck flags reading a subshell-modified `HOME`. Tests use isolated fake home directories and the Windows file-backed credential store so credential failures can be exercised without touching real secrets.
- Menu bar suite: run `swift test --package-path menubar` on macOS. The shell suite also exercises bundle and launch-agent installation with a fake toolchain.
